# 개발 로드맵

이 문서는 현재 저장소를 한 학기 안에 실제 시연 가능한 보안 분석 흐름으로 확장하기 위한 순서와 완료 기준을 정리합니다. 계획 항목은 실행 코드와 검증 결과가 확인될 때 구현으로 갱신합니다.

## 상태 기준

| 상태 | 의미 |
| --- | --- |
| 구현 | 실행 코드와 화면 또는 API가 현재 저장소에서 확인됨 |
| 기반 | 계약·인터페이스·화면 틀이 준비됨 |
| 다음 | 다음 구현 주기에 진행할 핵심 기능 |
| 보류 | 핵심 시연 이후 시간과 검증 결과에 따라 추가 |

## 현재 기준선

현재 실행 가능한 범위는 다음과 같습니다.

- React 웹과 FastAPI API 연결
- 개발용 Bearer 토큰 인증과 공통 오류 응답
- 자산 등록·조회·활성 상태 변경
- DB 기반 작업 큐와 단일 Python Worker
- SYSTEM_CHECK의 QUEUED → RUNNING → SUCCEEDED/FAILED 처리
- 가상 Inventory, Feed, Finding, Evidence와 고정 기대 결과
- 자산·작업·시험 예제 화면
- SQLite 로컬 실행과 PostgreSQL Docker Compose 구성
- 수집·정규화·판정·검색·LLM을 연결할 도메인 계약과 Protocol

시험 예제는 실제 서버를 수집하거나 CVE를 판정하지 않습니다.

## 1단계. 범위와 기준본 고정

목표는 분석 대상을 줄이고 판정 기준을 먼저 고정하는 것입니다.

- Ubuntu 릴리스 하나를 선택합니다. 22.04 또는 24.04 중 시험 환경에서 재현 가능한 값을 사용합니다.
- Apache2 또는 MySQL 중 하나를 첫 제품으로 선택합니다.
- 실제 서버 대신 JSON fixture로도 같은 인벤토리를 재현합니다.
- 지원하지 않는 릴리스·패키지·출처는 NEEDS_REVIEW 또는 별도 상태로 남깁니다.
- 패키지명, 바이너리·소스 구분, Debian 전체 버전, 자료 기준본 ID를 입력 계약에 포함합니다.

완료 기준은 지원 범위 문서화, 정상·취약·수정·정보 부족 사례 준비, 동일 입력에서 동일 결과 재현입니다.

## 2단계. 환경 수집과 자료 정규화

목표는 실제 판정에 필요한 두 입력을 공통 형식으로 만드는 것입니다.

- InventoryCollector를 우선 JSON fixture 구현체로 연결합니다.
- 이후 허용 대상, 호스트 키, 고정 읽기 전용 명령을 적용한 SSH 수집을 추가합니다.
- FeedNormalizer를 구현해 Ubuntu 공식 자료를 FeedSnapshot으로 변환합니다.
- 원문, 출처, 수집 시각, 해시, 정규화 버전과 가상 여부를 보존합니다.
- 부분 수집과 자료 갱신 실패를 완전한 목록으로 바꾸지 않습니다.

완료 기준은 인벤토리와 자료 기준본의 재생성, 입력 누락과 잘못된 버전의 구분, 갱신 실패와 이전 기준본의 동시 확인입니다.

## 3단계. 규칙 기반 영향 판정

목표는 AI 없이도 재현 가능한 판정을 먼저 완성하는 것입니다.

- AssessmentEngine의 assess 입력을 구현합니다.
- OS 릴리스, 패키지 종류, 패키지 이름, 아키텍처와 전체 버전을 대조합니다.
- Debian 버전 비교 규칙과 Ubuntu 수정 버전을 적용합니다.
- AFFECTED, FIXED, NOT_AFFECTED, NEEDS_REVIEW를 처리합니다.
- NOT_INSTALLED, COLLECTION_FAILED, PARTIAL_COLLECTION, NO_MATCHING_RECORD를 영향 없음과 구분합니다.
- 판정 이유, 비교 기준, 자료 기준본, 규칙 ID와 공식 근거를 함께 저장합니다.

완료 기준은 취약 버전·수정 버전·버전 누락·출처 불명확 사례 테스트와 판정 이유의 화면 표시입니다.

## 4단계. 결과 화면과 시연 흐름

목표는 입력부터 공식 근거까지 교수님이 짧게 확인할 수 있게 만드는 것입니다.

- findings 화면을 실제 API와 연결합니다.
- 자산, 패키지, CVE, 설치 버전, 수정 버전, 판정, 이유와 공식 링크를 표시합니다.
- 미확인·부분 수집·상충 근거를 별도 상태로 표시합니다.
- 수집·분석 작업의 상태와 오류를 작업 화면에서 확인합니다.
- 시험 자산 한 개로 요청부터 결과 조회까지 반복 가능한 시연 절차를 만듭니다.

완료 기준은 준비된 fixture를 이용한 3분 내 시연과 실제 결과·가상 예제의 명확한 구분입니다.

## 5단계. 근거 검색과 GPU 기반 설명

목표는 판정 결과를 모델이 임의로 바꾸지 않는 설명 기능을 추가하는 것입니다.

- 검색 범위를 선택 자산, 분석 ID, CVE와 자료 기준본으로 제한합니다.
- 문서 조각, 원문 위치, 출처 주소를 함께 반환합니다.
- LLM에는 확정된 판정과 검색된 근거만 전달합니다.
- 모델 출력의 인용 ID가 실제 근거에 존재하는지 백엔드에서 검증합니다.
- 모델 장애·시간 초과·근거 부족을 답변에 표시하고 판정 조회는 유지합니다.
- GPU는 로컬 모델 추론과 필요한 임베딩 생성에 사용합니다.

완료 기준은 설치 버전과 공식 근거가 포함된 답변, 근거 없는 확정 표현 차단, GPU 없이도 판정과 근거 조회가 가능한 구조입니다.

## 6단계. 대응 보고서

목표는 동일한 분석 기준본을 고정한 Markdown 보고서를 제공하는 것입니다.

- 분석 ID, 생성 시각, 판정, 이유, 수정 버전과 공식 출처를 포함합니다.
- 취약점 인사이트와 보고서가 같은 판정 기준본을 사용하게 합니다.
- 보고서 생성 실패가 판정과 근거 조회를 막지 않게 분리합니다.
- 화면에서 보고서 내용을 확인하고 Markdown으로 내려받게 합니다.

완료 기준은 화면의 판정·출처·기준 시각과 보고서 내용의 일치입니다.

| 영역 | 기본 담당 | 결과물 |
| --- | --- | --- |
| 전체 통합 | 통합 담당 | API·DB·Worker 연결, 실행 절차, 최종 시연 |
| 수집·정규화 | 수집 담당 | InventoryCollector, FeedNormalizer, fixture와 테스트 |
| 판정 엔진 | 판정 담당 | AssessmentEngine, 버전 비교 테스트, 판정 이유 |

| GPU·설명 | 통합 담당과 협업 | 모델 실행, 인용 검증, 취약점 인사이트 시연 |

담당자는 코드와 함께 입력 예시, 출력 예시, 테스트 방법과 교수님께 설명할 문장을 남깁니다.

## GPU 사용 계획

GPU는 취약점 판정 자체에 사용하지 않습니다. 판정은 규칙 기반으로 확정하고 GPU는 다음 작업에 사용합니다.

- 공식 근거 문서 임베딩 생성
- 자산·CVE·분석 기준으로 제한한 근거 검색 보조
- 판정 이유와 공식 근거를 자연어로 설명
- 선택 자산의 취약점 인사이트 생성
- 대응 보고서 문장 생성

GPU가 없어도 fixture, 규칙 기반 판정, 근거 조회와 고정 시연은 실행 가능하게 유지합니다.

## 범위 밖으로 둘 항목

- 모든 Ubuntu 릴리스와 모든 패키지 지원
- 실시간 침해 탐지와 무단 스캔
- 자동 패치·설정 변경·서비스 재시작
- 다중 조직·운영 계정·세밀한 권한 관리
- 고가용성·분산 Worker·예약 갱신
- 모델 추가 학습
- 근거 없는 자유로운 챗봇 응답

## 단계별 검증

| 기록 | 내용 |
| --- | --- |
| 입력 기준 | 자산·인벤토리·자료 기준본·파일 해시 |
| 실행 환경 | OS·Python·DB·모델·색인·규칙 버전 |
| 기대 결과 | 처리 상태, 판정, 이유, 인용, 오류 |
| 실제 결과 | API 응답, 저장값, 작업 ID, 소요 시간 |
| 재현 방법 | 실행 명령과 필요한 설정 |
| 제한 사항 | 미지원 입력, 자료 누락, 모델 장애 |

통합 인수 시험은 인수 시험 명세를 기준으로 수행합니다. 현재 시험 예제 통과를 실제 CVE 정확성 검증으로 해석하지 않습니다.

## 로드맵 갱신 규칙

다음 조건을 모두 확인한 경우에만 항목을 구현으로 바꿉니다.

1. 실행 코드가 저장소에 있습니다.
2. 정상 입력과 경계 입력을 검증했습니다.
3. 화면 또는 API에서 결과를 확인할 수 있습니다.
4. 실행 방법과 제한 사항을 문서화했습니다.
5. 실제 시연에서 같은 결과를 재현했습니다.
